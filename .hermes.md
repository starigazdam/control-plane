## OpenSpec workflow

Plan, review the plan, then implement. The full guide is
[`docs/openspec.md`](docs/openspec.md).

1. Before changing feature or behavior code, prepare an OpenSpec change with a
   proposal, a spec delta, a design, and tasks. Baseline specs under
   `openspec/specs/` keep describing existing behavior only.
2. Get an independent high-capability review of those artifacts. Use the named
   reviewer when the maintainer selects one, and do not pin a specific model
   globally. Confirm the actual model and provider, and bind the approval to
   the artifact revision that was reviewed. A requested model name, a pending
   process, or passing structural validation does not prove a review happened.
3. Resolve blocking findings. If the reviewed specification changes
   materially, review the changed revision again.
4. Get explicit human approval of the reviewed design.
5. Start implementation only after a separate explicit implementation
   instruction. Selecting an issue, approving a proposal, or merging planning
   artifacts does not authorize apply. Never create the initial proposal and
   implement it in the same worker run.
6. Keep implementation tests, exact-head CI, independent final review, human
   merge approval, and evidence-backed spec sync or archive as separate later
   gates. A specification review does not approve unimplemented code,
   deployment, merge, or archive.

## Rules

- Use feature branches; never push directly to `develop` or another default
  branch.
- Require green CI, independent high-capability review, and Michal's approval
  before merge.
- Every feature slice needs end-to-end coverage; implementation is staged
  around the repository's Aspire testing foundation.
- Keep public artifacts generic: do not add credentials, environment topology,
  or private infrastructure references to issues, pull requests, docs, or
  examples.

## Delivery guidance

- Deliver the smallest working, verifiable increment that meets the current request.
- Do not add speculative features, abstractions, or configuration for possible future needs.
- Preserve existing repository instructions and validate changed behavior with the narrowest relevant check.
