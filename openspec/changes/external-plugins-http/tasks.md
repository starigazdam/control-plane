## 2. Add the external plugins bridge

- [x] 2.1 Add the `ControlPlane.ExternalPlugins` project with its settings type, configuration binding, and solution and host references. Implement `IPluginServiceRegistration` so the bridge binds its section from the passed `IConfiguration`, registers a named client with `services.AddHttpClient("<name>")`, and keeps the configured plugin list for its `Register` call; verify `dotnet build src/ControlPlane.slnx` succeeds.
- [x] 2.2 Parse the static plugin list of `name` and `baseUrl` entries, validate the name grammar, require an absolute `http` or `https` `baseUrl` with no query, fragment, or userinfo, and fail startup on an invalid name, a duplicate name, or a missing or invalid `baseUrl`; verify each failure case stops startup with a clear error that names the setting.
- [x] 2.3 Fetch `GET /capabilities` once per plugin during registration with a 10-second timeout and one short-lived `HttpClient` because the container does not exist yet, and parse status provider ids and operation definitions. Treat a response that is not JSON or whose top-level shape omits `statusProviderIds` or `operations` as invalid capabilities; verify a fabricated plugin returns capabilities and a stalled plugin times out.
- [x] 2.4 Exclude a remote id that violates the id grammar (including a first character that is not a letter or digit), the reserved status provider id `bridge` under ordinal case-insensitive comparison, every entry of a duplicate status provider or operation id group (ordinal case-insensitive), an operation entry with a missing or wrongly typed required field, a wrongly typed optional field, an invalid parameter entry, or an `operations` element that is not an object, and a non-string `statusProviderIds` element. Report each exclusion as a `Warning` on `{name}.bridge`; verify each exclusion registers no capability and produces the `Warning`.
- [x] 2.5 Always register `{name}.bridge`: report `Healthy` on clean discovery and `Warning` with the fixed signal id `unreachable`, the fixed signal id `invalid-capabilities`, or the excluded capabilities otherwise. The provider reflects startup discovery only and does not change after startup. On an unreachable, non-2xx, or invalid capabilities response register no operations and keep the host up; verify the host starts and the overview shows the `Warning`.
- [x] 2.6 Implement the bridge adapters that normalize remote status providers to `IStatusProvider` and remote operations to `IOperation`, namespaced as `{name}.{remoteId}`; verify the exposed ids and definitions in a focused test.
- [x] 2.7 Implement the wire calls `GET /status/{id}?projectId={projectId}`, `POST /operations/{id}/validate`, and `POST /operations/{id}/execute` with the design payloads, resolving `IHttpClientFactory` for runtime calls. Use the remote id captured at discovery, percent-encoded as one path segment, in each path, and percent-encode `projectId`; verify requests and responses match the design mapping.
